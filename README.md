# clinical_mark: evaluating AI clinical suggestions against the patient's records

The evaluator answers three questions about an AI answer for an ICU patient: does it state false
facts, how close are its suggestions to what the clinicians did, and what did it miss. The patient's
own records are the gold standard. The fact-checking part follows VeriFact (Chung et al., "Verifying
Facts in Patient Care Documents Generated by Large Language Models Using Electronic Health Records",
NEJM AI 2026).

## Run

```bash
pip install numpy
python run.py --out-dir results_fixed                 # evaluate input/mimic_triples_fixed.json
python run.py --triples input/mimic_triples_open_s1.json --out-dir results_open_s1
bash run_all.sh                                       # rebuild every result and validation output
```

- `run.py` defaults to cloud models through `OLLAMA_API_KEY`: `deepseek-v4-pro:0813` splits, and
  `deepseek-v4-pro:0813`, `minimax-m3.1-flash`, `glm-5.3` vote as judges. It also needs a local Ollama
  with `bge-m3` (retrieval embeddings).
- `run_all.sh` rebuilds the older local-model results with `qwen2.5:14b` (atomizer) and the judge panel
  `gemma4:12b`, `llama3.1:8b-instruct-q4_K_M`, `qwen2.5:14b`. The fact judge and atomizer prompts changed on 2026-11-06, so it
  requests answers cached before that date again.
- Options: `--case M37067082`, `--limit`, `--retrieval hybrid|dense|bm25`, `--top-n 50`,
  `--ai-model ...`, `--judge-models ...`, `--judge-think gemma4:12b` (judges that answer in reasoning mode; empty for none),
  `--facts-all-judge` (ablation: every fact goes to the judges; no code checks, rule labels or administration guard),
  `--labels verifact` (VeriFact's three labels and definitions: no `unverifiable`, statements that would get it go to
  the judges with `prompts/fact_judge_vf.txt`, and a treatment the records mention but do not show given is
  `not_supported`; the default `clinical_mark` keeps this project's four labels).
- A full run without cache takes about an hour, mostly the reasoning judge. Model answers are kept in
  `<out-dir>/model_cache.jsonl` (one line per request: the request, the answer and the judge's
  reasoning); embeddings in `embeddings/`. Rerunning the same command resumes and gives the same result.

Each result folder holds `report.md` (metrics and per-case score sheets), `summary.json`,
`review_sheet.csv` (every item with its verdict and evidence), `cases/` (one JSON per case),
`atoms/` (the atomized AI answers) and `model_cache.jsonl`.

## Cases and records

- Cases: the earliest ICU stay of each of the 100 demo patients; decision time T = ICU admission +
  24 h; evaluable when the patient is still in the ICU at T (85 cases).
- The generator sees the 24 h before T. Facts are checked against the whole admission before T;
  a record counts only if its event time and, when present, its entry time are before T. Infusions
  and procedures still running at T are kept even when entered later, because MIMIC writes such a row
  when the interval ends (370 of the 378 running at T were stored at or after their end); they show
  only what was known at the start (start time, item, rate). eMAR events such as "Not Given" are not
  counted as doses.
- Actions are checked against clinician actions in (T, T + 24 h], cut at ICU discharge:
  prescriptions, eMAR administrations, infusions, procedures; therapies running across T count as
  continued.

**Repaired input.** `mimic_frozen_triples.json` kept only MIMIC `valuenum`, so text results in the
generator's prompt were lost ("NOT INTUBATED." became "Intubated", the ventilator mode "CPAP/PSV"
became "11"). `fix_input.py` restores them from MIMIC; `generate_answers.py` then regenerates the
answers. The evaluator itself always reads the records from MIMIC.

## Validating the evaluator

```bash
python make_annotation_set.py --run base,results_deepseek_cloud,input/mimic_triples_deepseek.json,14     --run s1,results_open_deepseek_s1_cloud,input/mimic_triples_open_deepseek_s1.json,6 --out annotation_set
# three clinicians label annotation_set/annotations.csv independently, blinded to the machine verdicts
python score_annotations.py annotation_set/annotations.csv --run base,results_deepseek_cloud     --run s1,results_open_deepseek_s1_cloud --out annotation_set/validation_report.md
python sensitivity.py results_fixed --triples input/mimic_triples_fixed.json --annotations annotation_set/annotations.csv --out validation/sensitivity_fixed
python stability_compare.py results_fixed validation/retest_fixed validation/stability_results_fixed.md
```

- `make_annotation_set.py`: per case, an HTML chart (admission records before the decision, clinician
  actions and measurements after it) and a label sheet with three annotator columns and an
  adjudication column. Machine verdicts are not shown. Labels follow the four-tier display: facts
  supported / not_supported / unverifiable; treatments and monitoring agrees / disagrees / undetermined;
  one "finding" row per abnormality the clinicians treated, mentioned / omitted (checks fact omissions).
  Each case is sampled into one answer set only; half of each set's cases have a not_supported fact.
- `score_annotations.py`: ground truth = adjudicated label or the annotators' majority. Reports
  inter-annotator agreement and evaluator vs ground truth: percent agreement, Gwet's AC1, Matthews
  correlation coefficient, per-label sensitivity / specificity / PPV / NPV, 95% bootstrap CIs over cases.
- `sensitivity.py`: re-judges the panel's facts with each retrieval method, N in {10, 25, 50, 100},
  and each judge (with and without reasoning).
- `stability_compare.py`: test-retest agreement of two runs of the same evaluation.

**Known-answer tests (no human labels).**

```bash
python make_controls.py
python run.py --triples input/control_error_injection.json --out-dir validation/controls/error_injection
python run.py --triples input/control_doctor_as_ai.json --out-dir validation/controls/doctor_as_ai
python score_controls.py
```

- Doctor as AI: each case's answer is replaced by the clinicians' own treatments after the decision,
  one suggestion per treatment class. All are true, so every non-match is a false alarm and vital
  recall should be 100%.
- Error injection: suggestions judged correct in `results_fixed` and `results_open_s1` are edited to
  carry one error (reversed abnormality, a drug from a group never given in the admission, continue
  -> discontinue, an added treatment from such a group) and evaluated one at a time; the share
  detected is the evaluator's sensitivity to that kind of error.

## Pipeline

| Stage | What happens | Decided by |
|---|---|---|
| 1. Atomize the AI answer | Split into fact / action / goal atoms. Premises hidden in actions ("assess causes of hypokalemia" presupposes hypokalemia; "continue X" presupposes X is running) become facts. A watch-for or a condition is not a premise ("monitor for signs of sepsis, including fever", "manage hyperkalemia if present"). | `qwen2.5:14b`, plus rule-based recovery of missed premises |
| 2. Check facts | Against the records of the current admission known before the decision time (VeriFact's reference EHR). | Labs, vital signs and ventilation status: code. Other statements: judge panel with a hybrid-retrieved reference context. |
| 3. Check actions | Against clinician actions recorded after the decision (24 h or until ICU discharge). | Monitoring: code checks for measurements. Treatments: code checks target (same class or the named drug) and direction (continue / stop / adjust); unclassifiable suggestions go to the judge panel. |
| 4. Omissions | Treatment classes the clinicians used, graded vital / okay, checked against what the AI suggested. | Code |

The atomizer never sees the records; each judge sees one atom and its retrieved records only.

**Retrieval.** For each statement, bge-m3 dense similarity and BM25 lexical scores are combined with
distribution-based score fusion; the top N records are passed to the judge in chronological order
with absolute date, time and source.

**Judge panel.** Three models from different families vote; the majority wins and a three-way split
falls back to the conservative label and is flagged for review. Models in `--judge-think` answer in
reasoning mode.

## Labels and metrics

- Facts: `supported`, `not_supported`, `not_addressed` (VeriFact's labels) and `unverifiable` (vague
  or hedged statements, alarm events, statements of necessity, urine results without a reference
  range). Fact accuracy = supported / (supported + not_supported). A judged "receiving / given X"
  statement keeps `supported` only if the records show X delivered in the 24 h before the decision
  (administration, device charting such as BiPAP or PCA settings, or running at T); a named drug must
  appear by name, a named class must match, a general group ("pain management") is met by any member.
- A fact that only reports a value ("Potassium is 3.4 mEq/L", "Sodium 128-133") is checked against the
  recorded values before the decision (lab and bedside, 24 h first), not against a direction the
  atomizer inferred; a value far outside every recorded value (likely another unit) is `unverifiable`.
  "Low-normal" counts as normal; "borderline" without a value is `unverifiable`. A diagnosis word that
  names a monitor setting ("desaturation limit", "alarms for desaturation") is not a finding.
- Treatments: `match`, `partial_match` (same aim and direction, another agent of the class or group),
  `not_done` (nothing corresponding, or the opposite direction: stop vs continued, increase vs
  decreased, a dose change never made, continued ventilation vs extubation),
  `condition_not_met`, `vague_target`, `unobservable`. Agreement (strict) = match / (match +
  partial_match + not_done). A suggestion that names a specific class within a group ("red blood
  cell transfusion") must match that class; "increase" / "decrease" must match the direction of the
  recorded rate change. A suggestion to stop a treatment does not count as covering it.
- Monitoring: `performed`, `not_performed`, `unobservable`; reported separately.
- Omissions: each treatment class the clinicians used is **vital** (marked vital in the rule file, or
  answering an abnormality present at the decision time) or **okay**. The main metric is vital recall;
  recall over the first three suggestions is also reported.

## Limitations

- A missing record does not prove something did not happen, and the clinicians' choice is not the only
  correct one. The evaluator does not judge whether a suggestion is clinically good.
- Design choices: a clinician order after the decision counts as a clinician action (the decision),
  whether or not it was given. Absence is taken as evidence in three places: "stop X" matches when no X
  is recorded after the decision; a conditional suggestion with no recorded action is
  condition_not_met; no ventilator charting for more than 6 h before the decision means not ventilated.
- Test-retest compares two independent judge runs (the retest was first run with an empty judge cache
  and keeps its own cache); it shows repeatability under fixed settings, not correctness.
- The evaluator's own accuracy against clinicians is not yet measured.
- Structured MIMIC-IV tables only; free-text notes would need a record atomization step.

## VeriFact baseline on the 85 cases (Route B)

VeriFact's fact checking, as in its code, run on the same 85 cases and the same fact atoms as this
evaluator (Claude's split standard, `reference/split_standard.csv`, 486 facts), so only the fact
checking differs. Plan and rationale: `VERIFACT_BASELINE.md`.

```bash
python run_baseline85.py --time-cut none   --out-dir results_baseline85/vf_hybrid_nocut   # VeriFact's whole-record setting
python run_baseline85.py --time-cut before --out-dir results_baseline85/vf_hybrid_cut     # same, records before T only
python score_baseline85.py REFERENCE results_baseline85/vf_hybrid_nocut results_baseline85/vf_hybrid_cut results_final_claude_split
```

| Path | Content |
|---|---|
| `cm/baseline.py` | VeriFact retrieval over record rows (dense; hybrid = top N dense + top N sparse, distribution-based fusion, identical texts once; rerank = hybrid + bge-reranker-v2-m3), full-text embeddings, VeriFact's absolute-time context |
| `run_baseline85.py` | One local judge (default `llama3.1:8b-instruct-q4_K_M`) with VeriFact's prompt and settings; no code checks, three labels; `--time-cut before / none`, `--retrieval-method dense / hybrid / rerank`, `--top-n` |
| `score_baseline85.py` | VeriFact's metrics (from `score_bhc.py`) against a reference (CSV `atom_id,label` or a run folder), per-label confusion, paired differences between runs; `unverifiable` counts as not addressed |

- Reference: the existing Claude reference is not independent of this evaluator: 199 of its fact
  labels come from this evaluator's code, and the rest were judged on this evaluator's retrieved
  records, so it favours this evaluator (`results_final_claude_split` scores 97.9% against it). A
  fair comparison needs a new reference judged on the full records before T, blind to both systems.
- `rerank` needs `pip install sentence-transformers torch` and downloads the reranker model (not
  installed yet). Admission start and end in the context are the earliest record and T (or the
  latest record without the time cut), since the demo data has no admissions table.

## eICU test set

The test set for the paper (`PAPER_PLAN.md`): 100 unit stays from the eICU Collaborative Research
Database Demo v2.0.1 (open access, ODbL; `data/eicu-demo/`), with answers from three generators given
time-stamped records. The system is frozen at tag `v1.0-dev85`; only the data adapter and item mapping
were added.

```bash
python make_eicu_cases.py                     # select cases (seed 20261117), write input/eicu_triples.json
python generate_answers.py --source input/eicu_triples.json --out input/eicu_triples_gpt-oss-120b.json --model gpt-oss:120b:cloud
python run.py --source eicu --triples input/eicu_triples_gpt-oss-120b.json --out-dir results_eicu/gpt-oss --labels verifact
python run_baseline85.py --source eicu --triples input/eicu_triples_gpt-oss-120b.json --atoms results_eicu/gpt-oss --time-cut before --out-dir results_eicu/vf_gpt-oss
bash run_eicu_all.sh cloud gpt-oss-120b deepseek-v4.1-flash qwen2.5-7b   # all systems, cloud judges
bash run_eicu_all.sh local gpt-oss-120b deepseek-v4.1-flash qwen2.5-7b   # all systems, llama3.1:8b
RESULTS=results_eicu_dx ATOMS_FROM=results_eicu bash run_eicu_all.sh factehr gpt-oss-120b deepseek-v4.1-flash   # FactEHR baseline
python score_factehr.py                       # FactEHR vs the vote, the evaluator and VeriFact -> results_eicu_dx/FACTEHR.md
```

`run_eicu_all.sh` writes `results_eicu/<generator>/`: `ours_vote` (the evaluator's split and the
three-model vote), `ours_pro` and `vf_pro_cut` (deepseek-v4-pro), `ours_llama`, `ours_llama_alljudge`,
`vf_llama_cut` and `vf_llama_nocut` (llama3.1:8b). All judge the atoms of `ours_vote`.

| Path | Content |
|---|---|
| `rules/eicu_items.json` | eICU labs, nurse and respiratory charting mapped to canonical (MIMIC-IV) item ids; free-text oxygen devices mapped to the device vocabulary of `rules/measures.json`; infusion and medication rules |
| `cm/records_eicu.py` | eICU rows in the evaluator's row format; synthetic clock (2100-01-01 at the unit admission time of day); rows known before T = unit admission + 24 h by event and entry offsets |
| `make_eicu_cases.py` | First unit stay, direct admission, still in the unit at T, labs and at least 24 charted rows before T; 100 by seed; the prompt lists every record of the 24 h before T with its time |
| `tests/test_records_eicu.py` | Synthetic eICU tables: time window, mapping, devices, ventilation status, infusion intervals, orders |
| `run_factehr.py` | Second published baseline: FactEHR's binary entailment prompt (verbatim, `prompts/factehr_entailment_binary6.txt`) and settings; premise = every record row before T, no retrieval; one judge (deepseek-v4-pro); two labels |
| `score_factehr.py` | FactEHR next to the vote, the evaluator and VeriFact on the same answer sets; three-label and binary scoring; `results_eicu_dx/FACTEHR.md` |

Dataset-specific rules, decided from the schema before any verdict:

- Infusions are charted about hourly with the current rate; consecutive equal rates form one
  interval, a rate of 0 ends it, and the last interval runs at T if charted within 4 h before T.
- eICU has no medication administration record: a scheduled order active at T counts as running, a
  one-time order as given at its start, a PRN order as an order only. The coded dosage field is not shown.
- Clinician actions after T are not built: the test set is for fact verification only.

## VeriFact-BHC track (MIMIC-III)

Scores fact judging against the clinician ground truth of MIMIC-III-Ext-VeriFact-BHC v1.1.0
(PhysioNet, credentialed), laid out like VeriFact's own code (github.com/philipchung/verifact, MIT,
commit f115d36). The plan is in `VERIFACT_BASELINE.md`. The MIMIC-IV pipeline above is unchanged.

```bash
pip install pandas pyarrow numpy        # irrCAC and scikit-learn only for the formula cross-check in tests
# release at data/physionet.org/files/mimic-iii-ext-verifact-bhc/1.1.0 (the path wget -r creates),
# or pass --release-dir / set VERIFACTBHC_DATASET_DIR
# 1. Replay check: VeriFact's judge, local Llama 3.1 8B, on the released Llama-8B contexts
python run_bhc.py --source-model Llama-8B --judge-models llama3.1:8b-instruct-q4_K_M --out-dir results_bhc/vf_llama8b_replay --sample 600
# 2. This project's judge (rules + three-model vote) on the released Llama-70B contexts
python run_bhc.py --judge-style ours --out-dir results_bhc/ours_panel_released --sample 600
# 3. VeriFact's judge on this project's retrieval
python run_bhc.py --context ours --out-dir results_bhc/vf_judge_ours_retrieval --sample 600
python score_bhc.py results_bhc/vf_llama8b_replay results_bhc/ours_panel_released results_bhc/vf_judge_ours_retrieval
```

|---|---|---|

| `prompts/verifact_system.txt`, `prompts/verifact_fewshot.txt` | `packages/llm_judge/.../prompts.py` | VeriFact's judge system prompt and few-shot prompt, verbatim (checked against the source) |

| `tests/test_bhc.py` | - | Synthetic mini release; prompt layout, context format, retries, metrics against irrCAC and scikit-learn; no model calls |

Differences from VeriFact that remain:

- Models: local Ollama models (Llama 3.1 8B q4 by default). VeriFact's Llama-70B is AWQ INT4 on vLLM;
  the release also holds Llama-8B, Gemma-3-12B, Qwen-3 and R1 verdicts for replay comparisons.
- Decoding: Ollama with a JSON schema instead of vLLM with Outlines; a fixed seed per sample.
- `--context ours`: no reranker (bge-reranker-v2-m3 is not in Ollama), BM25 in place of bge-m3 sparse
  weights, and regex sentence facts instead of semantic chunking + NLTK sentences or atomic claims.
  `--context released` has none of these differences.
- Reasoning models (VeriFact's second structured-output pass) are not reproduced.

- Data use: the release and everything derived from it (`data/physionet.org/`, `results_bhc/`,
  `embeddings_bhc/`) are in `.gitignore`. Only local Ollama models may judge it.
- The full release has 13,290 propositions; start with `--sample`.
- Not yet checked on the real release: the exact `human_gt` strings (unknown strings stop the run),
  the stored values of `fact_type`, `top_n` and `reference_only_admission`, and the note columns.
